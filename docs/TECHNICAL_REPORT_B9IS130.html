Abstract: This technical report details the analysis, architectural design, security engineering, implementation, testing, and deployment of KindredHeart, an end-to-end, full-stack Donation Management System (DMS). Developed using the MERN stack (MongoDB, Express.js, React, Node.js), the platform addresses critical sociotechnical challenges within charitable giving—specifically donor mistrust, opaque financial allocation, friction in multi-currency international donations, and administrative overhead for non-governmental organisations (NGOs). The system features an interactive, component-based user interface, an external exchange-rate web service integration for real-time currency conversion, a layered RESTful Application Programming Interface (API), and comprehensive Open Web Application Security Project (OWASP) Top 10 mitigation strategies, including salted bcrypt password hashing and stateless JSON Web Token (JWT) role-based authorization. Rigorous manual and automated test strategies are documented alongside production-readiness blueprints for cloud hosting on Render, Vercel, and MongoDB Atlas.

1. Introduction & Problem Statement

1.1 Context and Problem Domain

Charitable giving and philanthropic engagement represent vital mechanisms for societal welfare, disaster response, healthcare funding, and poverty alleviation. In recent years, digital fundraising platforms have largely supplanted conventional offline collection methods. However, non-profit organisations and independent cause organizers encounter substantial obstacles in donor conversion and retention. Research indicates that the predominant inhibitor of online charitable contributions is a pervasive deficit of public trust, stemming from high-profile charitable scandals, ambiguous fund utilization, and the perception of exorbitant administrative overhead (Breeze and Scaife, 2015; Sargeant and Woodliffe, 2007).

Furthermore, small-to-medium community charities frequently lack the capital and technical expertise to procure costly enterprise donor management software. Consequently, these grass-roots organisations rely on fragmented spreadsheets, unverified social media solicitations, or generic peer-to-peer portals that impose punitive transaction fees (often exceeding 5% to 8% per donation) while offering scant donor transparency.

1.2 Target Users and Stakeholder Personas

To ensure user-centred system architecture, three distinct primary stakeholder groups were defined:

  • The Donor (Public / Philanthropist): Seeking a reliable, accessible portal to discover vetted community causes, review financial allocation breakdowns, execute low-friction payments across domestic and international currencies (EUR, USD, GBP), and automatically retrieve downloadable/printable digital tax receipts.
  • The Campaign Organizer (Charity Officer / Community Leader): Requiring an intuitive administrative console to launch causes, establish realistic funding goals, upload multimedia evidence, track donor rosters in real-time, and post milestone progress reports.
  • The Platform Administrator (System Overseer / Compliance Moderator): Tasked with verifying organizer legitimacy, auditing transactions, managing categories, and moderating content to safeguard platform integrity.

1.3 Project Objectives

The objective of this project is to architect, develop, test, and document KindredHeart, an accessible, transparent, and scalable Information System that implements a decoupled MERN stack architecture adhering strictly to modular separation of concerns, exposes a CRUD-complete RESTful API supporting campaigns, user authentication, and transaction ledgers, consumes external RESTful web services to provide real-time currency exchange calculations, and enforces modern security mechanisms aligned with OWASP Top 10 benchmarks.

2. Requirements Analysis & Research Process

2.1 Domain Research and Market Gap Analysis

An empirical evaluation of existing donation platforms (e.g., GoFundMe, JustGiving, and iDonate.ie) was conducted to identify common UX and technical pain points. While large commercial platforms excel at payment gateway throughput, they exhibit two notable deficiencies: opaque fund utilization and international currency friction. Donors are rarely provided an explicit, itemised visualization of how their contributions are partitioned, and donors from foreign jurisdictions are frequently confronted with opaque bank exchange conversion fees at checkout without upfront clarity regarding base currency parity.

2.2 Functional Requirements (FR)

  • FR1 (User Management & Authentication): The system shall permit users to register, authenticate, and maintain sessions securely using JSON Web Tokens (JWT). The system must assign distinct roles (donor, organizer, admin).
  • FR2 (Campaign Management — Full CRUD): Organizers shall be capable of creating new campaigns, updating active causes, and soft-deleting cancelled initiatives.
  • FR3 (Interactive Donation Processing): The system shall enable donors to contribute funds using preset amounts (€10, €25, €50, €100) or custom inputs, select anonymous donation masking, and leave dedications.
  • FR4 (Real-Time Ledger & Progress Synchronization): Upon successful payment confirmation, the campaign's aggregate raised total and donor counter shall immediately increment atomically in the persistent database.
  • FR5 (Digital Tax Receipt Generation): The system shall automatically generate a unique, cryptographically identifiable transaction receipt (TXN-YYYY-XXXX) containing timestamp, donor identity, campaign reference, and deductible amount.
  • FR6 (External Currency Exchange Integration): The application shall fetch live FX exchange rates from an external REST API to compute dynamic target and contribution amounts across EUR, USD, and GBP.
  • FR7 (User Dashboards): Organizers shall access a dedicated portal showing aggregated campaign metrics; donors shall access a ledger detailing historical contributions.

2.3 Non-Functional Requirements (NFR)

  • NFR1 (Performance & Latency): Server response latency for all read queries (GET /api/campaigns) shall remain under 200ms under standard local network conditions.
  • NFR2 (Security & Confidentiality): User credentials must never be stored in plaintext. Passwords must be hashed using a computationally hard one-way hashing function (bcrypt). API routes must be protected against NoSQL injection, XSS, and CSRF.
  • NFR3 (Usability & Accessibility): The client interface must adhere to WCAG 2.1 Level AA contrast standards, incorporate semantic HTML5 structural elements, provide visible focus states for keyboard-only navigation, and render responsively across mobile, tablet, and desktop breakpoints.
  • NFR4 (Reliability & Resilience): In the event of external third-party API outage, the system must fail gracefully by falling back to cached exchange rates without degrading core donation processing.

3. System Architecture & Technology Justification

3.1 Architectural Pattern: Decoupled Layered MVC

KindredHeart utilizes a decoupled client-server architectural style. The client-side Single Page Application (SPA) and server-side REST API function as completely autonomous applications communicating exclusively over stateless HTTP/HTTPS using standard JSON payloads.

On the back end, the architecture implements the classic Model-View-Controller (MVC) / Layered Service pattern:

  • Routes Layer (src/routes/): Inspects incoming HTTP verbs and resource endpoints, dispatching execution to authorized controllers.
  • Middleware Layer (src/middleware/): Executes cross-cutting concerns including token extraction, cryptographical verification, role authorization, and central error translation.
  • Controllers Layer (src/controllers/): Contains pure application domain logic, orchestrating CRUD transactions, calculating funding metrics, and returning uniform HTTP status responses.
  • Data Models Layer (src/models/): Governs strict document schemas, virtual properties, index definitions, and pre-save lifecycle hooks using Mongoose ODM.

3.2 Technology Stack Justification (The MERN Choice)

MongoDB: Selected over relational alternatives due to its schema flexibility, native JSON (BSON) data alignment, and dynamic scalability (Chodorow, 2013). Charity campaigns inherently possess diverse structures—some contain nested fund allocations, dynamic milestones, or optional beneficiary fields that map naturally into document sub-schemas without requiring multi-table SQL joins.

Node.js & Express.js: Node.js provides an asynchronous, non-blocking, event-driven runtime environment powered by Google's V8 engine (Tilkov and Vinoski, 2010). Because donation systems predominantly handle I/O-bound operations, Node delivers exceptional concurrency and low memory overhead. Express.js provides a minimalist routing pipeline, facilitating clean separation of middleware and controllers.

React: Chosen for its declarative, component-driven paradigm and Virtual DOM reconciliation (Banks and Porcello, 2020). When a donor submits a contribution, the progress bar animates smoothly and the digital receipt modal mounts without triggering a jarring full-page browser reload.

4. Security Implementation & Threat Mitigation (OWASP Top 10)

Securing financial transactions and user identities is foundational to building trust. KindredHeart integrates explicit mitigations against prominent vulnerabilities cataloged in the OWASP Top 10 framework (OWASP Foundation, 2021):

  • A01: Broken Access Control: Strict server-side Role-Based Access Control (RBAC) is implemented via authMiddleware.js. The controller verifies whether campaign.organizer.toString() === req.user._id.toString() before any update or delete operation. Unauthorized requests are rejected with HTTP 403 Forbidden.
  • A02: Cryptographic Failures: Plaintext passwords are never persisted. A Mongoose pre-save hook intercepts password mutations and applies bcrypt hashing with 10 salt rounds. Furthermore, select: false ensures queries omit password hashes by default.
  • A03: Injection: Express routes utilize strict type checks and property destructuring. Inputs are validated, and Mongoose schema casting automatically rejects non-string payloads targeting typed fields.
  • A05: Security Misconfiguration: CORS middleware is explicitly configured with allowed origin headers, methods, and sanitized headers.
  • A07: Identification and Authentication Failures: Stateless authentication is achieved using JSON Web Tokens (JWT) signed with HMAC-SHA256 and strict expiration (7d).

6. Cloud Deployment Process & Configuration

To demonstrate production-grade deployment as required by the CA1 brief, KindredHeart is architected for seamless multi-cloud hosting leveraging free-tier platforms:

  • Data Tier: MongoDB Atlas (Cloud Database-as-a-Service on AWS eu-west-1 Ireland).
  • Backend API Tier: Render.com Web Service (Containerized Node.js environment).
  • Frontend SPA Tier: Vercel / Netlify (Global Edge Content Delivery Network).

All sensitive credentials and connection strings are managed strictly via environment variables (MONGODB_URI, JWT_SECRET, PORT, CLIENT_URL).

7. Critical Reflection & Limitations

The platform successfully fulfills all foundational requirements of the B9IS130 assessment brief, providing a complete CRUD lifecycle, robust authentication, external web service integration, and fund transparency visualizers. Limitations include simulated payment settlement rather than live merchant merchant clearing, synchronous currency rate fetching rather than a distributed Redis cache, and polling-based progress updates rather than full-duplex WebSockets.
